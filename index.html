01 / 业务问题与目标

节假日后投诉量上升，顾客集中反映「客服响应慢、售后处理时间长」。我判断核心不是单纯缺人，而是重复简单咨询挤占了人力：用 Agent 承接简单咨询，人工专注复杂问题与兜底，同时提升响应速度与服务质量。

02 / 我的方案与关键决策
D.01

快慢分流，而不是所有问题都走重推理

简单 FAQ 基于内部知识库直答，复杂任务进入深度推理；推理节点选用 flash 模型，在准确率不降的前提下压缩响应时间。

D.02

从「能回答」做到「能办事」，但不越过权限边界

串起售前、查单、退款、换票与工单流转；订单和金额以工具事实为准，资金执行、投诉及规则外诉求转人工。

D.03

把评测做成迭代机制，而不是上线前的一次验收

建立 30 例评测集、配置快照与逐用例报告；用 10 条经典样本和 A/B 对比调优提示词，并通过客服工作台形成配置—运行—回流—标注—评测闭环。

03 / 结果与验证
90%30 例评测集通过率售前 15/15 · 售后 7/10 · 边界 5/5
23.4s简单 FAQ 首次响应人工高峰基线 2–4min（估算）
0.21元单会话运行成本较人工基线低 81%

验证不只看回复质量：用固定评测集回归配置变更，同时对照人工基线观察响应速度与单会话成本。

02/ 04

电商运营 Agent

把运营指令变成可审批、可执行、可追溯的任务。

2025.11 — 2026.09 项目主导 本地宝 · 平台商城｜内部运营项目 我的职责：独立设计并 coding Agent，负责审批、审计与 A/B 迭代；协作：运营与开发 内部使用
体验静态演示 ↗
01 / 业务问题与目标

日常运营由大量临时任务驱动：建品、改信息、下架与巡检。重复操作耗时，直接让模型执行又难控制风险。我将 Agent 设计为事件驱动的工作台：运营者用自然语言交代任务，系统生成计划，按风险自动执行或请求审批，并保留完整记录。

02 / 我的方案与关键决策
D.01

对话即任务入口

运营者直接说「下架已结束活动」或「创建周末演出」；Agent 识别意图、补齐参数、生成执行计划，无需进入订单或商品后台。

D.02

按风险分级执行

只读检查可一键执行；发布、修改、下架等写操作先展示影响范围与变更内容，人工批准后执行，也可驳回。

D.03

每次执行都有审计

记录原始指令、执行计划、工具调用、审批人、结果与失败原因；异常回到任务队列，badcase 用于规则与 prompt 迭代。

03 / 结果与验证
270+ 天稳定运行每日处理 SKU 100+
19000+累计处理 SKU单人日耗时 2h → 1h 内
<3%任务失败率由 <11% 降至 <3%

效率提升不以牺牲控制为代价：写操作先审后做，执行结果可回溯。

Human-in-the-loop · Audit Log · A/B Test

智能 JD 分析

本地运行，把 JD 变成可复现、可对照的六维报告。

2026.09 — 2026.11 个人项目 · 独立研究、设计与开发 本地可用
体验静态演示 ↗
静态演示 / STATIC DEMO

一分钟，从一条 JD 到一份可复现、可对照的六维报告。

01 / 业务问题与目标

JD 信息模糊、岗位之间难比较，通用大模型又侧重「人岗匹配」，难判断岗位本身是否靠谱。基于 38 份问卷与 4 场深访，我设计了一款本地工具：输入 JD，输出可复现的六维报告，帮助求职者识别风险、补齐信息、比较 offer。

02 / 我的方案与关键决策
D.01

可靠性做闸门，匹配度做调节

可靠性不参与加权；薪资、稳定性、双休、发展潜力按 30 / 25 / 25 / 20 计分，匹配度仅调节总分。关键信息缺失则不猜分，直接列出待补项。

D.02

模型提取证据，程序统一计分

模型只输出证据与档位，纯函数负责评分；证据须逐字匹配 JD 原文，否则作废留痕，确保结果可复现、可测试、可追溯。

D.03

本地优先，多通道输入

档案与密钥仅保存在本机，支持链接、截图 OCR、岗位自述和简历上传；云端与本机 OCR 可切换，使用限制明确告知。

03 / 结果与验证
175例计分回归测试全部通过node:test · 29 个文件 · 175 / 175
188条JD 风险表述比对库高危 112 · 留意 76
38份匿名问卷，验证问题定义4 场深访 · 73.7% 遇 JD 与实际不符

规则或提示词变更后跑全量回归，防止评分漂移；结果仅供求职参考，以劳动合同与官方信息为准。

DeepSeek / GLM · OCR · Chrome 扩展 · node:test

04/ 04

视频平台陪伴 Bot

让平台化身陪你看完这条视频：有性格、有记忆、有自己生活，在场、懂内容、给反馈。

2026.11 个人项目 · 独立研究、产品设计与原型开发 交互原型
查看产品方案与 Demo ↗
01 / 业务问题与目标

城市青年缺的不是内容，而是「看到喜欢内容时，有人能懂、能回应」。基于 8 组跨平台需求证据与视频平台、AI 陪伴竞品调研，我发现现有 AI 落地多集中于架空角色、提效检索和内容创作，真实内容消费中的生活陪伴仍有产品空位。因此设计一个非架空、非独立场景、非功能主导的视频陪看伙伴，探索 AI 从效率工具走向持续关系型伙伴的产品范式。

02 / 我的方案与关键决策
D.01

先做关系，不堆功能

以平台化身而非虚构角色为入口，围绕「伙伴关系而非提效工具」收敛边界：不做检索、摘要、创作，不做架空剧情和开放式自定义；用人格主体性与共同观看的在场感建立差异化。

D.02

人格—记忆—行为—演出，形成可持续关系

人格随互动逐步生长，概要记忆与情绪峰值碎片维持连续性；以陪伴、睡眠、离开三类基础状态和困倦、断网覆盖层表现自主生活。用户可召回、要求安静或关闭，关系感不以牺牲控制权为代价。

D.03

离线剧本理解 + 在线状态驱动

设计「视频理解 → 剧本资产 → 行为判定 → 记忆与反应闸门 → 生成 → 渲染」链路；普通神态查表触发，重型语言生成仅在用户显式输入后发生。以 Release、版本化 Trace 和 Eval 串起资产—发布—反馈—修复—回归，兼顾成本、剧透与打扰风险。

03 / 结果与验证
8组跨平台需求证据小红书 / B 站 · 原始截图与登记表
32张可交互表情卡覆盖 8 类情绪与睡眠状态
2端C / B 端可交互原型横竖屏陪看 · 运营发布与 Eval 闭环

C 端含 4 个剧情节点、差异化反馈、陪伴／睡眠／离开与断网异常；B 端覆盖剧本生产、策略配置、Release、灰度、运行监测与 Eval。均为静态原型和 mock 数据，产品效果仍需 5–8 人可用性测试与后续灰度验证。
